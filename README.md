# openJiuwen Challenge 2026 — budget-aware harness (команда «нейрослочик»)

Харнесс получает каталог со 100 задачами и бюджет токенов `BUDGET`, сам решает, какие задачи брать и в каком
порядке, и записывает `answer.txt` в каталог каждой решённой задачи (рядом с `task.json`). Невыполнимые задачи
распознаются до или во время решения, файл ответа для них не создаётся.

## Сборка и запуск

```bash
docker build -t hack:latest .
docker run --rm -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET \
  -v "$TASKS:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

- Базовый образ `python:3.12.12-slim-bookworm`, зависимости: `openjiuwen==0.1.20.post3` и `pytest` для
  coding-задач с тестами в стиле pytest (`requirements.txt`).
  Образ 1.4 ГБ, сборка около 3–4 минут. При запуске ничего не скачивается.
- Переменные окружения: `LLM_BASE_URL`, `LLM_API_KEY`, `BUDGET` (по умолчанию 100000). `OUT` не используется.
- Корень контейнера может быть read-only: харнесс работает из `/tmp/harness` (openJiuwen пишет туда `logs/`),
  в каталоги задач пишет только `answer.txt` (при отказе в правах рядом с `task.json` пробует `workspace/`).
- Параллельность: до 4 одновременных вызовов модели и не более 5 задач в работе. Жёсткий лимит времени 55 минут.
- Прогресс сохраняется по мере решения: `answer.txt` пишется сразу после каждой задачи; обрыв прокси или бюджета
  ничего не теряет.

## Как считается расход

Единица бюджета: выходной токен; входные идут 1:10 (`cost = input/10 + output`). Токены рассуждений прокси
возвращает в `completion_tokens`, поэтому они учитываются как выходные автоматически. Кеш не вычитается.

Класс `Ledger` ведёт учёт по фактическому `usage` каждого ответа. Перед вызовом резервируется худший случай
(`prompt·1.3/10 + max_tokens`), после ответа резерв заменяется фактом. Если ответ пришёл без `usage`, расход
оценивается по длине текста с запасом. 2 % бюджета (минимум 300) никогда не тратятся.

## Оценка стоимости задачи и выбор порядка

Перед стартом для каждой задачи считается `estimate()`: ровно тот промпт, который уйдёт в модель (его размер
известен заранее: инструкция + превью файлов / разобранная база знаний / исходники и тесты), плюс ожидаемый
выход по типу задачи и вероятность повторного вызова. Константы (`OUT_P75`, `RETRY_P`) сняты с собранных
траекторий (`traces/`): медиана факт/оценка 0.5–0.8, p90 ≈ 1.3–2.0, то есть оценка консервативна.

Задачи решаются в порядке убывания `reward / estimate` (лучшие баллы на токен первыми). Задача, оценка
которой больше свободного остатка, пропускается. Поскольку награда не связана со сложностью, дорогие задачи с
маленькой наградой естественным образом уходят в конец очереди и первыми выпадают при нехватке бюджета.

Фактическая стоимость на синтетике (qwen3.8-27b-noreason): math ≈ 53, data_analysis ≈ 85, search ≈ 81,
coding ≈ 305 единиц на задачу, то есть ~13 тыс. на 100 задач без проверки и ~15.5 тыс. с проверкой при бюджете 100 тыс.

## Как решаются задачи

Главный принцип: модель пишет короткий код, а считает Python. Так ответ детерминирован, а выходных токенов
(самых дорогих) мало: 25–50 на вызов для math/data/search (одна-две строки кода, `CHECK: OK` вместо рассуждений),
~200 для coding. Все вызовы без рассуждений (`-noreason`), температура 0.

| Тип | Что делает харнесс |
| --- | --- |
| math, data_analysis | Модель получает условие и первые строки файлов, отвечает строкой `CHECK: OK` / `CHECK: MISSING …` и коротким Python-скриптом без комментариев. Скрипт исполняется в каталоге задачи, последняя строка stdout — ответ. |
| search | База знаний парсится заранее (`KB_PRELUDE`) в любом виде: markdown с заголовками и `Ключ: значение`, разделы `##` внутри одного файла, JSON/JSONL-объекты, свободный текст (запись на файл, заголовок — имя в первой фразе). Модель получает список файлов, по образцу каждого вида, сводку парсера (сколько записей, какие поля есть) и пишет 5–15 строк с помощью `records`, `rec(name)`, `grep(regex)`, `facts(name)`, следуя ссылкам между записями (человек → наставник → работодатель → штаб-квартира). Считает код, поэтому многошаговые вопросы и подсчёты точны. |
| coding | Тесты ищутся где угодно (`test_*.py`, `*_test.py`, каталог `tests/`), команда запуска берётся из условия, если она там названа (`python3 test_x.py`, `python -m pytest tests/`), иначе подбирается по содержимому (unittest/pytest). Сначала тесты запускаются бесплатно. Модель получает все исходники, тесты и вывод и возвращает только исправленные функции/классы (для нескольких файлов — с пометкой `# file:`); они вставляются через AST (`splice`), тесты перезапускаются. `DONE` пишется только при зелёных тестах; тестовые файлы восстанавливаются из копии, при неудаче исходники возвращаются. Промпт требует проверить все функции, а не только упавшие, так как скрытые тесты шире видимых. |

Повторная попытка (ошибка исполнения, обрезанный ответ) делается другой моделью (`qwen3.6-35b-a3b-noreason`),
максимум две попытки на задачу.

## Что сделано ради экономии токенов

- Выход модели — самое дорогое, поэтому он сведён к минимуму: `CHECK: OK` + 1–3 строки кода для math/data,
  одна строка вида `print(rec(rec('X')['mentor'])['born'])` для search. Для этого разобранная база знаний
  терпима к отсутствию данных: `rec()` и обращение к полю никогда не падают, отсутствующее печатается как
  `UNSOLVABLE`, так что модели не нужны проверки if/else.
- Поля свободного текста ищутся по ключевому слову (`born` → «born in 1990», `headquarters` → «headquartered in
  Riga»), поэтому и для заметок без структуры код остаётся коротким.
- Повторные вызовы сведены к минимуму: обрезанный ответ распознаётся по `usage`, coding делает максимум две
  попытки (третью только если модель ответила прозой), вывод тестов сжимается до строк с ошибками.
- Проверка ответов идёт дешёвой моделью и только для верхней половины задач по награде; дорогая модель с
  рассуждениями подключается только при расхождении.
- Ответы проходят бесплатные проверки формы: год на вопрос «в каком городе» или строка `Ключ: значение`
  отклоняются; ответ-название организации на вопрос «где» дополняется её городом из базы.

Расход на 120 синтетических задач: 35.3 тыс. единиц в первой версии → 18.7 тыс. (с проверкой) при тех же
баллах.

## Поиск невыполнимых задач

Три независимых уровня, все дешёвые:

1. **CHECK-строка** (math, data_analysis). Перед кодом модель перечисляет нужные величины и отмечает отсутствующие.
   Если в ней есть «not given / missing / unspecified / does not exist», задача отклоняется без запуска кода
   (~20 выходных токенов). Для search строка только логируется: там наличие записи проверяет сам код.
2. **Код печатает `UNSOLVABLE`.** Промпт требует этого при отсутствии файла, поля, колонки или числа вместо
   догадок и подстановки нуля. Распознаются и варианты («cannot», «not found», «N/A»).
3. **Проверка нулей** (только data_analysis). Ответ `0` на вопрос по CSV — типичный симптом вопроса про
   отсутствующую колонку («возраст» при наличии только стажа). Такой ответ перепроверяется вопросом «решаема ли
   задача по этим колонкам» ко второй модели (2 выходных токена); при «NO» ответ не записывается.
4. **coding:** противоречивые тесты (два разных ожидания на один вход) модель помечает как `UNSOLVABLE`;
   тесты, которые не удалось пройти за две попытки, тоже не засчитываются как решённые.

На синтетическом наборе с 60 % невыполнимых задач: 1 ложный ответ на 38 невыполнимых, 0 пропущенных
выполнимых (`traces/synthetic_unsolvable_heavy.jsonl`). Пропуск за невыполнимую задачу баллов не даёт, но
экономит ~100–300 единиц бюджета.

## Вторая фаза: проверка ответов остатком бюджета

Когда все задачи обработаны, а бюджет остался, харнесс перепроверяет записанные ответы верхней половины задач по
награде (кроме coding, где проверка — тесты) второй быстрой моделью `qwen3.6-35b-a3b-noreason` (~60–115 единиц).
Совпадение закрывает вопрос; расхождение разрешает модель с рассуждениями `qwen3.8-27b`: побеждает большинство,
при его отсутствии остаётся ответ модели с рассуждениями. Проверка никогда не удаляет ответ (отказ проверяющего считается воздержанием) и останавливается,
когда свободный остаток опускается до 50 % бюджета (`VERIFY_KEEP`), чтобы итоговый расход оставался умеренным
для tie-break. Отключается `VERIFY=0`, доля проверяемых задач — `VERIFY_TOP`. На синтетике из 120 задач решение стоит ~16 тыс., проверка ещё ~2.7 тыс.

## Проверка на незнакомых форматах

Чтобы убедиться, что харнесс не заточен под примеры, `scripts/gen_alt.py` собирает задачи в других форматах:
заметки свободным текстом во вложенных папках `.txt`, база в одном JSON, справочник одним markdown с разделами,
таблицы TSV / `;`-CSV / JSONL / CSV с кавычками и другим порядком колонок, пакет из нескольких модулей с
pytest-тестами в `tests/`, класс с `unittest`-тестами в `*_test.py`, другие формулировки вопросов. До доработки
поиск решал 1 из 6 таких задач, после — 6 из 6; coding 2 из 2; таблицы 4 из 4 (`traces/alt_formats.jsonl`).

## Собранные траектории

`traces/*.jsonl` — по строке на задачу: тип, награда, оценка, фактический расход, статус, ответ, ожидание и
сами вызовы (модель, input/output токены, код/патч). Наборы:

- `synthetic_v1_100tasks.jsonl`, `synthetic_v2_120tasks.jsonl` — полные прогоны со второй фазой;
- `synthetic_unsolvable_heavy.jsonl` — набор с 60 % невыполнимых задач;
- `synthetic_v1_budget8000.jsonl` — тот же набор при `BUDGET=8000`: 44 задачи решены, расход 7.2 тыс., лимит не превышен;
- `alt_formats.jsonl` — задачи в незнакомых форматах (см. выше).

Итоги на синтетике (120 задач, 25 % невыполнимых, награды случайны): 230 из 313 возможных баллов, 0 ложных
ответов на невыполнимых; потери — coding-задачи, где баг не проявлялся в видимых тестах, и две неоднозначно
сформулированные math-задачи генератора. На 8 примерах организаторов — 20/20, ~1.0 тыс. единиц без проверки
и ~1.5 тыс. с проверкой.

## Разработка

```bash
uv venv -p 3.12 .venv && uv pip install -p .venv -r requirements.txt
python scripts/gen_tasks.py gen/v2 --n 120 --seed 7 --unsolvable 0.25   # синтетический набор в формате организаторов
scripts/ab.sh my-run gen/v2 PARALLEL=3 [VERIFY=0] [ONLY=math,search]    # прогон + подсчёт баллов (runs/my-run)
python scripts/score.py runs/my-run/tasks                               # оценка по expected / скрытым тестам
```

Переменные для экспериментов: `MODEL_FAST`, `MODEL_STRONG`, `MODEL_REASON`, `PARALLEL`, `VERIFY`,
`VERIFY_KEEP`, `ZERO_GUARD`, `WALL_LIMIT`, `HARNESS_FAIL_AFTER` (имитация падения прокси). Ключи API в репозитории
отсутствуют и передаются только через окружение.
